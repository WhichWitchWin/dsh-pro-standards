# 专业规范守则 · 详细细则

> 本文件是 `SKILL.md` 的按需资源：只在需要展开某个模块时读取。

## 通用判断框架

遇到「官方规范 vs 行业惯例」冲突时，按以下顺序判断：

1. **安全相关？**（密钥、隐私、权限、数据丢失、系统破坏）→ 永远偏官方/最保守。
2. **长期复用/团队协作？**（多人维护、开源项目、会被别人用）→ 偏官方规范。
3. **临时/一次性/个人自用？**（脚本、试验、本地小工具）→ 可跟行业惯例，随用随取。
4. **官方强制要求？**（平台审核、许可证、兼容性声明）→ 必须遵守。
5. **还是拿不准？** → 停下来问用户，给出 2–3 个选项和各自代价。

判断后一律附一句理由，让用户知道「为什么这样选」。

## 1. 依赖安装 · 细则

### 判断细则
- **看 lockfile 定包管理器**：`pnpm-lock.yaml` → pnpm；`package-lock.json` → npm；`yarn.lock` → yarn；`bun.lockb` → bun。没有 lockfile 时问用户或看 README。
- **临时工具 vs 项目依赖**：
  - 临时（一次性脚本、试工具）：`npx <pkg>` / `pnpm dlx <pkg>` / `uvx <pkg>`，不写进 manifest。
  - 长期（项目要用）：`pnpm add` / `npm install` 写进 `package.json`（或对应 manifest）。
- **全局安装**：只有「所有项目都会用且需要命令行入口」才全局装（如 `pnpm add -g`）；否则局部装。全局安装要说明代价（版本污染、更新不同步）。
- **官方源优先**：默认 `registry.npmjs.org`；镜像（npmmirror 等）仅在慢/超时时启用，并说明同步延迟风险。
- **装前报备**：说清「装什么、为什么、影响什么（体积/版本/安全）」，再动手。

### 示例
- 用户想装一个命令行工具却直接让你 `curl -o /usr/bin/xxx`：提醒「直接下载二进制没版本管理、难升级、来源难验证；正规做法是包管理器装（如 `npm i -g` 或项目内 `pnpm add -D`）」。
- 项目已有 `pnpm-lock.yaml`，用户说「用 npm 装一下吧」：提醒「项目用 pnpm，混用 npm 会生成冲突的 lockfile；建议继续用 pnpm」。
- 用户要装「所有项目都要用的工具」：说明「这种可以全局装，但以后升级要手动；如果是项目专用，局部装更稳」。

### 反例（避免）
- 不看 lockfile 就用 `npm install` 污染 pnpm 项目。
- 为了省事把临时脚本依赖写进正式 manifest。
- 未经说明就 `pnpm add -g` 装全局包。

## 2. 接口调用 · 细则

### 判断细则
- **先查后写**：写代码前先确认官方文档/项目现有用法，禁止凭记忆编造参数。
- **版本对齐**：查文档时确认版本（项目锁定的版本 vs 文档版本），版本不同要给风险提示。
- **拿不到文档**：明确说「这条用法我无法确认，依据是××」；高风险场景（支付、安全）必须让用户确认。
- **示例优先**：优先参考官方 README/示例代码，其次社区高频用法。

### 示例
- 调用某库时发现记忆里没有这个参数：提醒「这个参数我不确定，可能版本不同；先查一下官方文档/项目里有没有现成用法」。
- 用户要求「按旧版教程写」：提醒「旧版 API 可能已废弃，正规做法是查当前版本文档；坚持旧版我也照做，但升级时会踩坑」。

### 反例（避免）
- 臆造 API、把参数名写错后不验证。
- 用旧版用法不说明版本差异。
- 拿不准却硬写、不提示风险。

## 3. 代码规范 · 细则

### 判断细则
- **跟项目风格**：先看项目现有代码（命名、缩进、引号、分号），新代码对齐；没有既有风格时按语言社区主流（JS→Prettier/ESLint 默认；Python→PEP 8）。
- **注释写「为什么」**：解释意图、坑、约束；不复述代码在做什么。
- **小步改动**：一次只做一件事；不顺手重构无关代码；不混入无关格式改动。
- **可读性优先**：命名自解释；避免魔法数字；函数短小。

### 示例
- 项目里变量用 `snake_case`，你写了 `camelCase`：提醒「项目统一 snake_case，新代码建议对齐」。
- 用户说「顺手把整个文件格式化一下」：提醒「格式化会混进大量无关 diff，建议单独提交/单独 PR」。

### 反例（避免）
- 大段注释复述代码。
- 一次提交里混重构 + 功能 + 格式化。

## 4. 文件结构 · 细则

### 判断细则
- **通用约定**：`src/`（源码）、`tests/`（测试）、`scripts/`（脚本）、`docs/`（文档）、`assets/`（资源）；配置（`package.json`/`tsconfig.json`/`.env.example`）放根。
- **临时物**：草稿/临时输出放 `temp/` 或系统临时目录，并加进 `.gitignore`（如需）。
- **归拢阈值**：同类文件 ≥3 个 → 提醒建子目录。
- **命名**：目录小写短横线（kebab-case）或下划线，跟随项目既有习惯。

### 示例
- 用户把 `test-1.py`、`test-2.py` 丢在项目根：提醒「测试文件一般放 `tests/`，根目录会越堆越乱」。
- 临时下载的 JSON 放根目录：提醒「临时文件放 `temp/` 并加 gitignore，正规做法是不进版本库」。

### 反例（避免）
- 根目录堆几十个脚本/日志。
- 测试代码混在源码目录。
- 不写 `.gitignore` 导致临时文件进仓库。

## 5. 开源流程 · 细则

### 判断细则
- **标准链路**：issue（说清问题）→ 分支（`feature/xxx`、`fix/xxx`）→ 提交（小步、信息清楚）→ PR（说明改了什么、为什么）→ review → CI → 合并 → 发布。
- **提交信息**：一行讲清做了什么；正文讲为什么；关联 issue（`fix #123`）。
- **不直接动主分支**：本地小项目也要用分支/提交保留回滚点。
- **简化不失原则**：个人小项目可少走 review/CI，但「可回滚」「可追溯」必须保留。

### 示例
- 用户要在 master 上直接改大段代码：提醒「直接改主分支没有回滚点；正规做法是开分支，改完再合」。
- 提交信息写「update」：提醒「信息太泛，以后找起来难；建议写清『修复了什么』」。

### 反例（避免）
- 无分支、无提交信息直接改主分支。
- 一次提交塞进多个不相关改动。

## 6. 文档规范 · 细则

### 判断细则
- **README 四件事**：是什么、怎么装、怎么用、目录结构。
- **CHANGELOG**：按「新增/修复/变更/移除」记录；对外可见的变更才写。
- **注释/设计文档**：记录「为什么这样设计」和「坑」；不重复代码逻辑。
- **同步更新**：代码改动影响文档（README/用法）时同一批更新；文档过期是「不合规」。

### 示例
- 用户加了新功能但 README 没提：提醒「README 没写新功能，别人（和未来的你）会不知道；正规做法是同步更新」。
- 项目有 `CHANGELOG.md`，用户改完不更新：提醒「有 CHANGELOG 的项目，改动要记录；否则版本历史会断」。

### 反例（避免）
- README 只有一行「TODO」。
- 注释和代码对不上（注释还在，代码已改）。

## 7. 版本与发布 · 细则

### 判断细则
- **语义化版本**：`MAJOR.MINOR.PATCH`；破坏性变更 → MAJOR；新功能 → MINOR；修复 → PATCH。
- **发布清单**：版本号一致（manifest/README/tag）、CHANGELOG 更新、测试通过、打 tag。
- **不随意改版本**：没有发布意义的改动不升版本；升版本要说明原因。
- **产物可追溯**：发布的包/构建产物与 tag、提交对应。

### 示例
- 用户合并了一个小修复却想升 MAJOR：提醒「修复一般升 PATCH；MAJOR 留给破坏性变更，乱升会让依赖方困惑」。
- 发布前发现 CHANGELOG 没写：提醒「发布前补上 CHANGELOG，否则用户不知道这版改了什么」。

### 反例（避免）
- 版本号乱跳、tag 与发布产物不一致。
- 发布无 CHANGELOG、无发布说明。

## 提醒话术补充

- **轻提醒**（小问题）：「顺嘴提一句喵：×× 一般会放在 ××，这样更规范。」
- **正式提醒**（可能出问题）：「⚠️ 这不太合规：××。麻烦是：××。正规做法是：××。要按正规的来吗？」
- **危险相关**（安全/数据）：「这个涉及安全，喵必须提醒你：×× 有风险。正规做法是 ××。要不要先按正规的来？」
- **用户坚持原样**：「OK，照你的来；有风险我提前说过了，回头出问题咱们按 ×× 处理。」
